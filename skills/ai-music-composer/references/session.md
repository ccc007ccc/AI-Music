# Hosted authorized-task session

Use this protocol when the host exposes `CompositionSessions` instead of the expert CLI task-file workflow.

For the CLI adapter, the host starts an evaluator process with
`--role evaluator`, then attaches its stored report to a separate composer process with
`--role composer --critique <stored-report.json>`. Attachments are validated
before the composer process emits its initial authorization response. Read one
JSON response line after successful initialization, then exchange one
request/response per line. Read [the protocol document](../../../docs/cli-session-protocol.md) when implementing the transport.

## Host actions

1. Read the current Project revision and selected target tracks/ranges.
2. Construct a `CompositionTask` from the user's request. Keep destructive flags and track creation authority explicit; do not let the model fill them in implicitly.
3. Call `authorize_composition_task(task)`. If it returns `rejected`, explain the deterministic violations or ask the host/user to correct the task.
4. Give the model the returned task snapshot as planning context and retain only the opaque `task_id` as the authority handle.

## Evaluator and model actions

- The composing model reads context/events and drafts a proposal against the
  authorized task's revision.
- After rendering/listening, a separate evaluator (another model invocation or
  trusted perceptual adapter) submits one structured `critique` report against
  the same revision. Include the task's `brief_id`; each observation needs
  `location`, `observation`, and `consequence`; use `proposed_revision` for a
  concrete next experiment. The evaluator records one `modify` or `preserve`
  decision and rationale for every observation, using the brief's style context
  rather than a universal threshold. A `modify` decision must identify a track
  or tick range so execution is verifiable.
- The composing model then links `based_on_critique_id` and acknowledges every
  evaluator decision in `critique_responses` with a rationale describing
  implementation. The disposition is already stored in the critique and is
  not a field the composing model can override; it is not asked to make the
  quality decision itself. Once the host attaches a critique, omitting the link
  is rejected; there is no creator opt-out. A first proposal is allowed only
  before any critique is attached.
- Call `review_authorized_proposal(task_id, proposal)` for every revision.
- Fix deterministic violations and implement the evaluator's stored decisions.
  Rust requires material patch impact at each `modify` observation's location;
  `preserve` does not require changing that location. Do not send a modified
  task back with the proposal.
- Call `apply_authorized_proposal(task_id, proposal)` only for the exact proposal that reviewed `ready`.
- After a successful application, treat the task ID as consumed and obtain a new authorized task for a later revision or a newly selected region.

## Lifecycle guarantees

- The host stores a private copy of the task; mutating the returned JSON snapshot cannot broaden scope.
- A stale project revision blocks review/application until the host and model reread context and authorize a fresh task.
- A rejected proposal leaves the project and task authority active, so the model can revise within scope.
- A recorded critique leaves the Project and task authority unchanged. It is
  bounded to the task's tracks/ranges and can be linked from a later proposal
  with `based_on_critique_id`.
- A successful proposal consumes the task; revocation and project replacement/loading invalidate it.
- The host should not expose low-level `apply_patch` to a model tool. GUI editing may retain direct Rust commands as a separate trusted adapter.
- Never ask a model-facing host to enable `--allow-authorize`; it exists for trusted orchestration only.
- If a response has error code `project_changed`, discard all task IDs, reread context/events, and request a newly authorized task.

The exact serialized shapes are generated by `musicctl schema authorized-composition-task`, `task-authorization`, `session-request`, and `session-response`. The Tauri command names currently are `authorize_composition_task`, `review_authorized_proposal`, `apply_authorized_proposal`, and `revoke_composition_task`. Critique authoring is intentionally absent from the model-facing Tauri invoke handler; a desktop evaluator must use a trusted host-side adapter.
